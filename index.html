The principles that shape
every decision I make

These aren't buzzwords. They're the mental models I apply every day when building interfaces people actually use.

01

Clarity over visual noise

Every element I add must earn its place. If a user has to think about what something does, I've already failed. Good UI makes the obvious feel inevitable.

UX Principle
02

Systems over one-offs

I don't build pages — I build systems. Every component I write is reusable, every token I set is consistent, because the next feature should be faster to ship, not slower.

Engineering Principle
03

UX driven by real usage

I obsess over how real users interact — not how we imagine they will. Feedback loops, error states, loading skeletons, and edge cases are features, not afterthoughts.

Product Principle
04

Performance as design

A slow interface is a broken interface. Load time, render performance, and interaction latency are design constraints, not technical footnotes. Speed is part of the product.

Performance Principle

Code I write today will be read by someone else tomorrow. I write for clarity, add comments that explain intent, and structure features so future developers move faster, not slower.

Engineering Principle

Working software beats perfect plans. I push a v1 that solves the real problem, gather feedback, then improve. Iteration beats planning in circles. Done is better than perfect.

Full Case Study

Candidate Assessment Player

The core product of Select10X — built from zero in 6 weeks as the sole frontend developer.

Problem Statement

HR teams at Select10X needed a reliable, distraction-free environment to conduct structured online assessments for candidates. Existing third-party tools had poor mobile support, no customization, and high failure rates — causing candidate drop-off and unreliable data.

Constraints

  • No design team, no design specs — had to design in the browser
  • 6-week deadline from zero to production
  • Single frontend developer
  • Had to support MCQs, subjective answers, and coding challenges simultaneously
  • Needed to be reliable on 3G connections in rural areas of India

My Approach

I started with user flows on paper to map every state the exam could enter — not started, in progress, paused, auto-submitted, manually submitted, error. Then built a React component architecture where each question type (MCQ, subjective, coding) was an independent renderer, making it testable in isolation and extensible for new types later.

The most critical decision was the "trust layer": auto-saving every answer to both the API and localStorage on every change. This meant a network failure wouldn't lose candidate progress. The system would recover and sync on reconnection.

Key Decisions

  • Per-section timers: Each section had its own countdown, preventing candidates from spending all time on easy questions.
  • Optimistic UI for answers: Answers were stored locally first, then synced — so the UI was always responsive regardless of API latency.
  • Anti-cheat detection: Tab-switch events triggered a warning banner (3 warnings = auto-submit). Fullscreen was enforced on entry. These were frontend-only guardrails, communicated clearly to candidates upfront.
  • Progressive enhancement: Core functionality worked without JavaScript for accessibility, enhanced by JS where supported.

HR Analytics Dashboard

Turning raw assessment data into actionable hiring intelligence for recruiters.

Problem Statement

Recruiters had no visibility into aggregate data — they knew individual candidate scores but couldn't see patterns: which questions had 90% failure rates, which assessments took longest, what the pass/fail distribution looked like across roles.

My Approach

Mapped recruiter decision-making workflows before touching code. Identified the three questions they asked most often: "Who passed?", "How hard was it?", "How did this week compare to last?". Built the dashboard around those questions — not around the data available. Added CSV export to bridge the gap with existing Excel-based reporting workflows.
